# Personal AI Knowledge Agent 改进实施计划

更新日期：2026-08-28
适用基线：`v0.1.1`

本文把架构评估结论拆成可独立评审、可回滚、可验收的增量。优先验证真实产品价值，不以增加 Agent 数量作为里程碑。

## 执行原则

1. 每个迭代保持 `python scripts/verify.py` 通过；
2. 数据库 Schema、配置格式或安全边界变化必须提供迁移和负向测试；
3. 真实 Vault、查询、Prompt、证据正文和凭据不得进入 Git、CI artifact 或观测事件；
4. 新能力先建立评测基线，再决定是否进入默认路径；
5. 大模块按稳定接口逐步拆分，不进行一次性重写。

## M1：真实但脱敏的检索评测

目标：判断用户能否稳定找到正确笔记，而不只验证代码路径可运行。

状态：已完成。真实 Vault 在 Git 忽略目录中建立 82 条查询并分层划分为 66 条 tuning 与 16 条独立 test；keyword、FastEmbed BGE 中文 vector 与 hybrid 均已完成调参与一次性独立 test。Hybrid 保持 keyword 的 92.31% Recall@10、把 Chunk Recall 从 75% 提升到 83.33%，但延迟更高，因此保留为显式可选入口。

步骤：

1. 定义 `retrieval_dataset_v2`，增加语言、查询类型、期望路径和可选期望 Chunk（已完成）；
2. 从真实使用场景整理至少 50 个脱敏查询，覆盖中文、英文、标签、Wiki Link、同义表达和无答案问题（已完成，本地数据不进入 Git）；
3. 为 keyword、vector、hybrid 分别生成报告（已完成）；
4. 比较查询拒答门槛和 RRF 权重（已完成；RRF 权重在 tuning 上无可测差异，保留 1:1）；
5. 只在独立评测集改善且延迟门禁通过后更新默认参数（已完成决策：keyword 仍为默认，hybrid 显式启用）。

验收标准：固定数据集可复跑；报告包含 Recall@K、MRR@K、无答案误召回率和 P50/P95；基线不保存原始私人查询。

## M2：记忆反馈闭环

目标：用用户决策验证 Memory Candidate 是否值得长期保存。

步骤：

1. 增加匿名化决策原因枚举，例如重复、过细、不准确、敏感和表达需修改；
2. 支持“编辑后批准”，并保留原候选与最终内容的本地审计关系；
3. 写回前展示目标路径和 Markdown diff；
4. 聚合接受率、编辑率、冲突率与拒绝原因，不记录候选正文；
5. 增加撤销或修订已批准记忆的工作流。

验收标准：每个候选仍需明确决策；敏感候选不能通过编辑绕过治理；写回漂移保护保持有效。

## M3：后台任务与恢复体验

目标：Research 不长期占用 Web 请求，并让用户看得懂执行和失败状态。

步骤：

1. 定义应用层 Task Runner 接口，Web 路由只负责创建任务；
2. 首版使用本地进程内 worker 和现有 SQLite 租约，不引入外部队列；
3. 增加任务状态轮询、步骤进度和安全错误类别；
4. 验证进程重启、重复提交、租约过期、取消和恢复；
5. 只有出现多主机需求时再评估独立队列。

验收标准：创建 Research 请求快速返回；重启后任务可恢复；同一任务不会被两个有效 owner 同时提交结果。

## M4：可维护性与数据库演进

目标：降低大模块修改风险，并为后续版本兼容建立边界。

步骤：

1. 引入 Ruff 和静态类型检查，先记录基线再逐模块收紧；
2. 为 SQLite 增加 Schema version、迁移 runner、迁移前备份提示和升级测试；
3. 按接口拆分 `application.py`、`rate_limiter.py`、`observability.py` 和 Web routes；
4. 对持久化 Artifact、Provider Response 与评测报告增加显式 Schema；
5. 增加旧版数据库升级以及未知新版本拒绝测试。

验收标准：已有 CLI 和 Web 契约不变；迁移可重复执行；模块拆分前后的全量测试结果一致。

## 延后项及启动条件

- 动态 Planner：只有评测显示固定计划的问题分解质量是主要瓶颈时启动；
- 多 Agent：只有单 Workflow 出现可量化的并行、上下文隔离或权限隔离瓶颈时启动；
- 外部数据库或任务队列：只有个人规模 SQLite 在真实负载下无法满足延迟或并发目标时启动；
- 公网个人模式：只有完成身份认证、授权、租户隔离、审计与运维设计后启动。
